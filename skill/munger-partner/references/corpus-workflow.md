# 语料生产与审查

## 状态门

`raw → cleaner → chunker → corpus → extractor → model mapper → case matcher → candidate → critic → verifier → verified | rejected`

- `raw/`：L0 原始文件或不可变来源记录，只做完整性、指纹与来源登记，不改写内容。
- `corpus/`：L1 只保存原文、中文、出处、时间、位置与来源等级，不保存解释。
- `candidates/`：机器提取的候选原理，可有缺失字段和待核实标记，不可被当成权威知识。
- `verified/`：来源定位、上下文、归因、模型归并与反向审查均通过。
- `rejected/`：保留条目与拒绝理由，避免未来换名重复进入。

生产者不能批准自己的 Candidate。审查者应独立查看原始来源，而不是只读候选摘要。

## 知识单元内容顺序

原话 → 原理 → 反例 → 边界 → 出处。

没有可靠反例或边界时允许留空并写明待研究；禁止生成貌似真实的案例填空。

## Verified 的硬条件

- 原始来源存在且可访问；作者/发言者归因正确。
- 定位信息足以让第三方复查。
- 引文与上下文一致，没有用截句改变原意。
- 解释与原文分开，推断程度被标注。
- 已搜索重复模型；能归入已有模型时未新建模型。
- 真实案例的主体、时间与因果表述有证据；相关性没有写成因果性。
- 审查者身份、日期和结论已记录。

## 逆向审查问题

1. 来源是否真实且定位可复现？
2. 删除前后文后，意思是否被改变？
3. 这是新模型，还是旧模型换名？
4. 反例中的因果是否真的成立？
5. 解释是否超出了证据？
6. 什么最可能让这条知识误导用户？

仓库的 frontmatter 使用 JSON 对象；JSON 同时是合法的 YAML 1.2 子集，便于无第三方依赖校验。具体字段见根目录 `schemas/knowledge-unit.schema.json`。
